rules_docker_compose

Bazel rules for running integration tests which use Docker-Compose to setup networked infrastructure.

Setup

bazel_dep(name = "rules_docker_compose", version = "{version}")

docker_compose = use_extension("@rules_docker_compose//docker_compose:extensions.bzl", "docker_compose")
docker_compose.toolchain(
    name = "docker_compose_toolchains",
    version = "2.24.0",
)
use_repo(docker_compose, "docker_compose_toolchains")

register_toolchains(
    "@docker_compose_toolchains//:all",
)

Overview

rules_docker_compose provides Bazel rules for integrating Docker-Compose into your build and test workflows. These rules enable you to:

  • Merge and validate docker-compose configurations using the docker_compose_yaml rule, which combines multiple YAML files and/or inline Starlark configuration, and ensures all referenced images have corresponding loader targets
  • Define compose configurations in Starlark using the docker_compose_config helper, which provides structured parameters mirroring the Compose Specification (services, networks, volumes, configs, secrets)
  • Run docker-compose interactively with the docker_compose_binary rule, which loads images and forwards arguments to docker-compose (e.g. bazel run :compose -- up -d)
  • Run integration tests with the docker_compose_test rule, which loads images, starts services, waits for them to be running and healthy, runs your test binary, and cleans up containers on every exit path
  • Verify image integrity by recording each image's manifest digest, config digest and layer DiffIDs at build time, tagging loaded images by digest rather than by name, and checking both the images and the running containers against those records.

The rules integrate seamlessly with rules_oci and rules_img, allowing you to use container images built with Bazel in your docker-compose configurations. They handle the complete lifecycle of docker-compose services during testing: image loading and verification, service startup with health checks, container verification, and cleanup.

How it works

The rules split the work into three stages, and the boundary between them is the point of the design: everything that reaches a network happens first, everything that is checked happens at build time, and the test only ever confirms what the build already decided.

  1. Fetching happens in repository rules only. Images enter the build through oci.pull or img.pull, pinned by digest, and the compose binary comes from the toolchain. Nothing contacts a registry once repository fetching is done.
  2. Resolution happens in build actions. docker_compose_yaml merges the compose files, matches every image: reference to a loader target, records the identities of each image that survive a docker load (the OCI manifest digest, the config digest and the layer DiffIDs), and writes a loadable tarball per image. It emits two yamls: the merged file with your original tags, which is a plain compose file you can share, and a test copy where each loader-backed image is rewritten to a content-derived tag with pull_policy: never.
  3. Execution happens in the test. The runner loads each tarball if its content is not already present, tags the image by digest with its unique tag, and verifies the result. It then starts compose, waits for every service to be running and healthy, verifies that each container runs the image ID it just checked, runs your test binary, captures the compose logs and tears the project down on every exit path.

Philosophy

  • Tags are names, not identities. A tag in a shared daemon can be re-pointed by any other test, developer or CI job. The rules never locate an image by the tag declared on its loader. They locate it by digest and then prove, twice, that what runs is what was built.
  • The compose file stays a compose file. You write image: postgres:16 as you would anywhere, and Bazel decides what postgres:16 is through a pull and a loader that claim that name. The merged yaml with original tags works with plain docker compose outside Bazel.
  • A test cannot depend on the network. Every image must come through a loader. A reference without one is a build error, unless it is pinned to a digest and the target opts in with allow_registry_images, which is deliberately the uncomfortable path.
  • Sharing a daemon is safe by construction. Tests that use the same built image share one content-addressed tag and one image, which is harmless because the tag names immutable content and images are never removed. Tests that use different images never share a name, because the digest is in the name. Projects are named after the target, so containers and networks stay separate.
  • The environment is inherited, not guessed. DOCKER_HOST, DOCKER_CONTEXT, DOCKER_CONFIG and the TLS variables pass from the shell running bazel test into the test, so contexts, rootless daemons and Docker Desktop on Linux behave the same under Bazel as in a terminal. Bazel tests run with a fixed PATH; a docker binary outside /usr/bin or /usr/local/bin needs --action_env=PATH or RULES_DOCKER_COMPOSE_ENGINE_BINARY.

See Providing images for how to declare images with rules_oci and rules_img, and the examples for complete workspaces.

Why not to use these rules

These rules are designed for integration testing scenarios where you need to test against real networked services. However, they come with trade-offs that may not be suitable for all use cases:

  • Requires network access: Tests carry the requires-network and no-remote-exec execution requirements and cannot run in fully sandboxed or remote environments. This means tests may be slower and less reproducible than pure unit tests.

  • Docker dependency: Tests require a Docker daemon reachable from the host machine. The compose binary is downloaded hermetically, but the daemon cannot be. The Docker endpoint variables (DOCKER_HOST, DOCKER_CONTEXT, DOCKER_CONFIG and friends) are inherited from the invoking shell so contexts, rootless daemons and Docker Desktop work under bazel test.

  • Resource tracking limitations: Bazel cannot track all resources created by docker-compose (spawned containers, networks, volumes). Tests tear their project down on every exit path, but loaded images are deliberately kept, since other tests may share them. It's highly recommended to use resource tags to limit test execution and prevent resource exhaustion.

  • Host ports are assigned at test time: The host side of every published port is left to the daemon when a test runs, and the resulting address is passed to the test through RULES_DOCKER_COMPOSE_HOST_<SERVICE>_<PORT>. Tests therefore cannot collide on ports, but a test must read its service addresses from the environment rather than hard-code them. The declared ports still apply to bazel run.

  • No registry access at test time: Every image must be provided through an oci_load or image_load target so that all fetching happens in repository rules. Registry images are only permitted when pinned to a digest and explicitly opted into.

  • Platform-specific behavior: Container behavior may vary across different platforms and Docker versions, potentially affecting test reproducibility.

Consider using these rules when you need to test interactions with real services, but prefer lighter-weight alternatives for fast, hermetic unit tests.

Every image a compose file references must be provided through a loader target listed in images. The loader is where the image's content is pinned; the compose file only names it. How to declare loaders, the tag contract and the supported providers are documented on the docker_compose_yaml rule. This page covers the module-level setup that goes with it.

Which rules_oci version

Up to and including rules_oci 2.3.0, the BUILD file that oci.pull generates loads from @aspect_bazel_lib, which under bzlmod is only visible if your root module also declares it (bazel-contrib/rules_oci#575). Releases from 2.3.1 on fix this, but at the time of writing none of them is on the Bazel Central Registry. Until one is, point the module at a release tarball directly rather than adding aspect_bazel_lib to your own dependencies:

archive_override(
    module_name = "rules_oci",
    integrity = "sha256-JD6sh+xB1o0dnm0hiEpQ7CjgMfcCsLn83H+Xw/PVOJo=",
    strip_prefix = "rules_oci-2.3.3",
    urls = ["https://github.com/bazel-contrib/rules_oci/releases/download/v2.3.3/rules_oci-v2.3.3.tar.gz"],
)

Overrides only apply in the root module, so this has to live in each consuming workspace; the examples in this repository do the same. Once a 2.3.1+ release is on the registry, delete the override and bump the bazel_dep version.

docker_compose_binary

load("@rules_docker_compose//docker_compose:docker_compose_binary.bzl", "docker_compose_binary")

docker_compose_binary(name, images, yaml)

Creates a runnable target for invoking docker-compose with a generated configuration.

This rule consumes a docker_compose_yaml target and produces an executable that:

  1. Loads the container images recorded by the docker_compose_yaml target, tags each by digest with the names declared on its loader, and verifies them against the build output
  2. Runs docker-compose -f <yaml> <args...> forwarding all command-line arguments

Use this rule when you need to interactively manage docker-compose services (e.g. bazel run :compose -- up -d, bazel run :compose -- down).

Example:

load("@rules_docker_compose//docker_compose:defs.bzl", "docker_compose_binary", "docker_compose_yaml")
load("@rules_oci//oci:defs.bzl", "oci_load")

oci_load(
    name = "my_service.load",
    image = ":my_service",
    repo_tags = ["my-service:latest"],
)

docker_compose_yaml(
    name = "compose_yaml",
    yamls = ["docker-compose.yaml"],
    images = [":my_service.load"],
)

docker_compose_binary(
    name = "compose",
    yaml = ":compose_yaml",
    images = [":my_service.load"],
)

Then run with:

bazel run :compose -- up -d
bazel run :compose -- down
bazel run :compose -- ps

docker_compose_test

load("@rules_docker_compose//docker_compose:docker_compose_test.bzl", "docker_compose_test")

docker_compose_test(name, data, allow_registry_images, delay, env, env_inherit, ephemeral_ports,
                    images, interpolate, interpolation_env, startup_timeout, test, test_args, yamls)

Runs a test with docker-compose services.

This rule starts docker-compose services, waits for them to be ready, runs a test binary, and then tears down the services. The test lifecycle is:

  1. Loading each image's tarball (skipped when the content is already present), tagging it by digest with a content-derived unique tag, and verifying the result against the identity recorded at build time
  2. Starting services with docker-compose up against a YAML that references only those unique tags with pull_policy: never
  3. Waiting for every service to be running, and healthy when it declares a healthcheck
  4. Verifying that every container runs the image ID verified in step 1
  5. Running the test binary with optional arguments
  6. Capturing compose logs and running docker-compose down, on every exit path

Images are never located by the tags declared on loaders, so a tag that something else re-pointed cannot leak into a test. Images that other tests share are safe because the unique tag names immutable content and images are never removed.

Ports

Host ports are the other shared resource on a machine running many tests. By default the test yaml drops the host side of every published port, the daemon assigns a free one at startup, and the runner hands the result to the test through the environment:

VariableValue
RULES_DOCKER_COMPOSE_HOST_<SERVICE>_<PORT>host:port the container port is reachable at, e.g. 127.0.0.1:49153
RULES_DOCKER_COMPOSE_PORT_<SERVICE>_<PORT>the host port alone

<SERVICE> is the compose service name upper-cased with anything but letters and digits replaced by _, and <PORT> is the container port. ${NAME} references in test_args and in the test target's env are expanded against these at test time, so a test can be told -host $${RULES_DOCKER_COMPOSE_HOST_NGINX_80} without knowing the port in advance. Two tests publishing the same declared port therefore no longer conflict, and the declared port keeps working for bazel run. Set ephemeral_ports = False to opt out.

Each run also uses its own compose project name, the target-derived name plus a random suffix, so concurrent runs of one target, or a run overlapping a crashed predecessor, never share containers or networks. Network and volume names derived from the project follow suit; names set explicitly in the compose file, like container_name, are kept as written and remain the user's responsibility.

The test requires network access and a Docker daemon reachable from the host. The Docker endpoint variables are inherited from the invoking shell.

Images are declared through oci_load or image_load targets in images, and every services.*.image value must equal a tag declared on one of them. The docker_compose_yaml rule documentation describes the contract, the supported loaders and the rules_img requirements in full; passing a single docker_compose_yaml target as yamls is the simplest way to share one set of images between a yaml, a test and a binary.

The test is normally an ordinary *_test target written with the language's test framework and tagged manual, so bazel test //... runs it only through this rule, with the services up. Its args and env are honored, which keeps the service address next to the test that reads it.

Example:

load("@rules_docker_compose//docker_compose:docker_compose_test.bzl", "docker_compose_test")
load("@rules_oci//oci:defs.bzl", "oci_load")
load("@rules_python//python:defs.bzl", "py_test")

oci_load(
    name = "my_service.load",
    image = ":my_service",
    repo_tags = ["my-service:latest"],
)

py_test(
    name = "my_service_test",
    srcs = ["my_service_test.py"],
    env = {"SERVICE_HOST": "localhost:8080"},
    # Only meaningful with the services running, so only run via :integration_test.
    tags = ["manual"],
)

docker_compose_test(
    name = "integration_test",
    yamls = ["docker-compose.yaml"],
    images = [":my_service.load"],
    test = ":my_service_test",
    delay = 2,  # Wait 2 seconds after containers start
)

docker_compose_yaml

load("@rules_docker_compose//docker_compose:docker_compose_yaml.bzl", "docker_compose_yaml")

docker_compose_yaml(name, data, out, allow_registry_images, config, ephemeral_ports, images,
                    interpolate, interpolation_env, yamls)

Merges docker-compose configurations and validates image references.

This rule uses docker-compose config to merge one or more docker-compose YAML files (and/or an inline Starlark configuration) into a single, canonical configuration. It also validates that all images referenced in the configuration have corresponding loader targets specified in the images attribute.

At least one of yamls or config must be provided. When both are given, they are merged together using docker-compose config (the config JSON is applied on top of the YAML files).

The merged YAML preserves the original image tags declared in your inputs — it is diff-reviewable and safe to share outside Bazel (e.g. check it into version control, hand off to a teammate's docker compose -f invocation, etc.).

For each image with a registered loader, the merger ALSO records the identities that survive a docker load (the OCI manifest digest, the image config digest and the layer DiffIDs), writes a loadable tarball of the image, and emits a second YAML where services.*.image references are rewritten to the content-derived tag <repo>:rdc-<manifest digest> with pull_policy: never. That rewritten YAML is consumed only by docker_compose_test, which loads the tarball, tags the image by digest and verifies it before and after the services start. docker_compose_binary (and the default output of this rule) use the original tags.

Images

Every services.*.image value must equal a tag declared on a loader target listed in images; that string is the whole contract between the compose file and Bazel. The loader is where the image's content is pinned, through an oci.pull or img.pull by digest, while the compose file only names it. So image: postgres:16 keeps working unchanged outside Bazel and, inside Bazel, resolves to whatever digest the pull declares.

LoaderSourceTag attribute
oci_loadrules_ocirepo_tags
image_loadrules_imgtag, tag_list or tag_file

Only the image content behind a loader is used: the OCI layout of an oci_load, or the tarball output group of an image_load. The loader's own script is never run. For image_load, the base image's img.pull must therefore use layer_handling = "eager" (or "lazy") rather than the default "shallow", so every layer is available to build the tarball.

A referenced image without a loader is an error, unless it is pinned to a digest (<repo>@sha256:<digest>) and allow_registry_images is set.

Example with rules_oci:

load("@rules_docker_compose//docker_compose:docker_compose_yaml.bzl", "docker_compose_yaml")
load("@rules_oci//oci:defs.bzl", "oci_load")

# `@my_image` comes from an `oci.pull` in MODULE.bazel, pinned by digest, or from an
# `oci_image` built in this repository.
oci_load(
    name = "my_image.load",
    image = "@my_image",
    repo_tags = ["my-app:latest"],
)

docker_compose_yaml(
    name = "compose",
    # References `image: my-app:latest`.
    yamls = ["docker-compose.yaml"],
    images = [":my_image.load"],
)

Example with rules_img:

load("@rules_docker_compose//docker_compose:docker_compose_yaml.bzl", "docker_compose_yaml")
load("@rules_img//img:image.bzl", "image_manifest")
load("@rules_img//img:load.bzl", "image_load")
load("@rules_img_images.bzl", "image")

# The `img.pull` behind `image("my_base")` must set `layer_handling = "eager"`.
image_manifest(
    name = "my_image",
    base = image("my_base"),
)

image_load(
    name = "my_image.load",
    image = ":my_image",
    tag = "my-app:latest",
)

docker_compose_yaml(
    name = "compose",
    yamls = ["docker-compose.yaml"],
    images = [":my_image.load"],
)

Public images need no change to the compose file. Pull them by digest and let the loader claim the name the yaml already uses:

oci_load(
    name = "postgres.load",
    image = "@postgres",  # oci.pull(..., digest = "sha256:...")
    repo_tags = ["postgres:16"],
)

load("@rules_docker_compose//docker_compose:docker_compose_config.bzl", "docker_compose_config")

docker_compose_config(services, networks, volumes, configs, secrets)

Encode a docker-compose configuration as a JSON string.

Parameters mirror the top-level keys of the Compose Specification. The returned string is suitable for passing to the config attribute of docker_compose_yaml.

PARAMETERS

NameDescriptionDefault Value
servicesA dict mapping service names to their configuration dicts. Each value follows the Compose services.<name> schema (image, ports, environment, volumes, depends_on, etc.).{}
networksA dict mapping network names to their configuration dicts. Follows the Compose networks.<name> schema.{}
volumesA dict mapping volume names to their configuration dicts. Follows the Compose volumes.<name> schema.{}
configsA dict mapping config names to their configuration dicts. Follows the Compose configs.<name> schema.{}
secretsA dict mapping secret names to their configuration dicts. Follows the Compose secrets.<name> schema.{}

RETURNS

A JSON-encoded string representing the docker-compose configuration.
